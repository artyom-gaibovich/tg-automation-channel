# Команда: Извлечение правил архитектуры

Изучает фактическую архитектуру проекта по исходному коду и формирует документ правил `docs/rules/architecture.md`. Не зависит от конкретного LLM-агента — это процедурная инструкция для исполнителя (агент или разработчик).

## Назначение

Определить **фактический** архитектурный стиль проекта (слоистая, чистая, гексагональная, transaction script и т.п.), направление зависимостей, состав слоёв, способ управления транзакциями и межмодульное взаимодействие. Результат — нормативный документ, выведенный из кода, а не из ожиданий.

Стиль не предполагается заранее: он распознаётся по структуре пакетов, импортам и сигнатурам. Если код не соответствует ни одному «чистому» шаблону — это фиксируется как гибрид с описанием фактических свойств.

---

## Входные параметры

- Без обязательных аргументов — анализируется весь репозиторий.
- Необязательный аргумент `scope` — путь к подкаталогу (например, конкретный микросервис или модуль), чтобы ограничить анализ.

---

## Источники в коде

| Что смотреть | Зачем |
|--------------|-------|
| Дерево `internal/`, `cmd/`, `pkg/`, `configs/` | Группировка по слоям или по доменным модулям |
| Имена пакетов (`domain`, `application`, `infrastructure`, `usecase`, `persistence`, `ui`, `grpc`) | Наличие и назначение слоёв |
| Импорты между пакетами | Фактическое направление зависимостей |
| Интерфейсы репозиториев и их реализации | Разделение Read/Write, инверсия зависимостей |
| Сигнатуры UseCase / сервисов (`Execute`, `Input`, `Output`) | Способ оркестрации бизнес-операций |
| Управление транзакциями (Unit of Work, `pgx.Tx`, `Begin/Commit/Rollback`) | Где и как живут транзакции |
| Точки межмодульного взаимодействия (вызовы, события, gRPC-клиенты) | Допустимые способы связи модулей |

## Алгоритм

1. Определить корень анализа (весь репозиторий или `scope`).
2. Построить карту пакетов: для каждого каталога — имя пакета, его роль, во что он импортирует.
3. По карте импортов установить **направление зависимостей** между слоями и проверить, есть ли нарушения (например, `domain`, импортирующий инфраструктуру).
4. Классифицировать стиль: сопоставить наблюдаемую структуру с известными шаблонами (layered / clean / hexagonal / package-first по доменам / transaction script). Зафиксировать признаки, по которым сделан вывод.
5. Выделить повторяющиеся инварианты: что всегда в `domain`, что в `application`, что в `infrastructure`; как именуются UseCase; где объявлены интерфейсы.
6. Описать управление транзакциями как наблюдаемый паттерн.
7. Описать межмодульное взаимодействие: только через интерфейсы/события или есть прямые импорты.
8. Сформулировать каждое наблюдение как правило с ID-префиксом `ARCH`.
9. Записать документ `docs/rules/architecture.md` по формату из [template-rules.md](./template-rules.md).
10. Проверить документ по чек-листу.

---

## Что выявлять

- Архитектурный стиль и признаки, по которым он определён
- Состав слоёв и зона ответственности каждого
- Направление зависимостей и явные запреты (что какому слою импортировать нельзя)
- Где объявляются и где реализуются интерфейсы (инверсия зависимостей)
- Разделение чтения и записи, если присутствует
- Структура UseCase: метод, Input/Output, единичность операции
- Паттерн управления транзакциями
- Правила межмодульного взаимодействия
- Группировка кода: по слоям или по доменным модулям

## Выходной артефакт

- Файл: `docs/rules/architecture.md`
- Префикс правил: `ARCH`
- Формат: см. [template-rules.md](./template-rules.md)
- Каждое правило сопровождается фрагментом реального кода проекта (путь к файлу указывается рядом с примером)

---

## Ограничения

- Источник — **только код проекта**; запрещено переносить правила из внешних эталонов или из других документов проекта.
- Запрещено выдавать желаемую архитектуру за фактическую: если код противоречив, документ описывает противоречие.
- Если слой или паттерн в коде отсутствует — он не упоминается как правило (либо отмечается «в проекте не обнаружено»).
- Команда не меняет исходный код — только создаёт/обновляет документ правил.
