# Команда: Извлечение правил форматирования (Prettier)

Изучает конфигурацию форматировщика Prettier и фактическое оформление кода проекта и формирует документ правил `docs/rules/prettier.md`. Процедурная инструкция для исполнителя (LLM-агент или разработчик), переиспользуемая между проектами, где применяется Prettier.

## Назначение

Зафиксировать фактические нормы форматирования кода: значения опций Prettier (ширина строки, отступы, кавычки, точки с запятой, висячие запятые, скобки), способ запуска форматирования, интеграцию с ESLint и редактором, а также область применения (какие файлы форматируются, какие игнорируются). Документ выводит правила из конфигурации Prettier и подтверждает их фактическим оформлением кода.

---

## Входные параметры

- Без обязательных аргументов — анализируется весь репозиторий.
- Необязательный аргумент `scope` — путь к подкаталогу для ограничения анализа.

---

## Источники в коде

| Что смотреть | Зачем |
|--------------|-------|
| `.prettierrc` / `.prettierrc.json` / `.prettierrc.js` / `prettier.config.js` / поле `prettier` в `package.json` | Значения опций форматирования |
| `.prettierignore` | Область применения: что исключено из форматирования |
| npm-скрипты `format`, `format:check` в `package.json` | Как запускается форматирование и проверка |
| Версия `prettier` в `devDependencies` | Совместимость набора опций |
| Интеграция с ESLint (`eslint-plugin-prettier`, `eslint-config-prettier`, `plugin:prettier/recommended`) | Как форматирование увязано с линтингом |
| Настройки редактора (`.vscode/settings.json`, `.editorconfig`) | Автоформат при сохранении, согласованность с Prettier |
| Реальные `*.ts`/`*.js` файлы | Подтверждение, что код соответствует объявленным опциям |

## Алгоритм

1. Определить корень анализа (весь репозиторий или `scope`).
2. Найти конфигурацию Prettier и прочитать все объявленные опции (`printWidth`, `tabWidth`, `useTabs`, `semi`, `singleQuote`, `quoteProps`, `trailingComma`, `bracketSpacing`, `arrowParens`, `endOfLine`, `bracketSameLine` и др.).
3. Прочитать `.prettierignore` и зафиксировать область применения.
4. Зафиксировать команды запуска форматирования из npm-скриптов и охватываемые пути/шаблоны.
5. Проверить версию Prettier (значения по умолчанию менялись между мажорными версиями — например, `trailingComma` и `arrowParens`).
6. Зафиксировать интеграцию с ESLint и, если есть, с редактором (`.editorconfig`, автоформат при сохранении); при конфликте `.editorconfig` и Prettier отметить его.
7. Сверить несколько реальных файлов с объявленными опциями; при расхождениях (код не отформатирован) отметить это явно.
8. Сформулировать правила с префиксом `FMT`; каждое правило — конкретная опция с её значением и следствием.
9. Записать `docs/rules/prettier.md` по формату из [template-rules.md](./template-rules.md) и проверить по чек-листу.

---

## Что выявлять

- Значения ключевых опций: `printWidth`, `tabWidth`, `useTabs`, `semi`, `singleQuote`, `quoteProps`, `trailingComma`, `bracketSpacing`, `arrowParens`, `endOfLine`, `bracketSameLine`
- Область применения: игнорируемые пути (`dist`, `node_modules`, сгенерированный код), охватываемые шаблоны из скрипта `format`
- Команды запуска: `format` (запись) и `format:check` (проверка), если есть
- Версия Prettier и зависимость дефолтов от неё
- Интеграция с ESLint (`plugin:prettier/recommended`, отключение конфликтующих правил через `eslint-config-prettier`)
- Интеграция с редактором и `.editorconfig`, конфликты между ними
- Соответствие фактического кода объявленной конфигурации

## Выходной артефакт

- Файл: `docs/rules/prettier.md`
- Префикс правил: `FMT`
- Формат: см. [template-rules.md](./template-rules.md)
- Каждая опция подтверждается фрагментом конфигурации с путём к файлу, а по возможности — примером отформатированного кода

---

## Ограничения

- Источник — **только конфигурация и код проекта**; дефолтные рекомендации Prettier не переносятся как правила, если они не заданы явно (кроме явного указания, что значение унаследовано от дефолта версии).
- Если Prettier в проекте не настроен — это фиксируется как «в проекте не обнаружено», без выдумывания правил.
- Опции самого линтинга (не форматирования) описываются командой [extract-ts-lint-test-rules.md](./extract-ts-lint-test-rules.md), а не здесь.
- Команда не меняет конфигурацию и код — только создаёт/обновляет документ правил.
