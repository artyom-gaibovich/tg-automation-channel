# Команда: Извлечение правил логирования

## Назначение

Зафиксировать, какое логирование используется в проекте и как оно устроено: библиотека логгера, формат вывода, уровни, способ передачи логгера через контекст, паттерн middleware-декоратора для логирования вызовов сервиса, структура полей сообщения. Документ выводит нормы из реального кода логирования, а не из ожиданий.

---

## Входные параметры

- Без обязательных аргументов — анализируется весь репозиторий.
- Необязательный аргумент `scope` — путь к подкаталогу (например, конкретный микросервис) для ограничения анализа.

## Источники в коде

| Что смотреть | Зачем |
|--------------|-------|
| `tools/logging/logging.go` | Библиотека логгера (go-kit `log` + `level`), JSON-формат, фабрика `NewLogger`, фолбэк-логгер |
| `WithContext` / `FromContext` | Передача и извлечение логгера через `context.Context` |
| `getLevel` (маппинг уровней) | Соответствие строковых уровней (`emerg`, `err`, `info`, `debug`…) уровням `level.Allow*` |
| `pkg/echo/logging.go`, `pkg/health/logging.go` | Паттерн middleware-декоратора логирования вызовов сервиса |
| Интерфейс `logged` / метод `Log()` | Как DTO предоставляют поля для лога |
| Вызовы `level.Info`/`level.Warn`/`level.Error`, `log.With` | Уровни в коде и обогащение лога полями (`domain`, `method`, `took`, `code`) |
| `configs/config.go` (секция `logger`) | Конфигурация уровня и формата времени |
| `init()` в пакете логирования | Инициализация фолбэк-логгера и фильтра уровня |

## Алгоритм

1. Определить корень анализа (весь репозиторий или `scope`).
2. Найти пакет логирования (`tools/logging`) и определить используемую библиотеку и формат вывода (JSON, синхронная запись в stdout).
3. Разобрать фабрику логгера: как задаётся уровень, формат времени, как навешивается метка времени.
4. Зафиксировать маппинг строковых уровней на уровни библиотеки и поведение фолбэк-логгера.
5. Разобрать передачу логгера через контекст (`WithContext`/`FromContext`) и поведение при отсутствии логгера в контексте.
6. Разобрать middleware-декоратор логирования в `pkg/*/logging.go`: какие поля добавляются, как выбирается уровень по результату вызова, как замеряется длительность.
7. Зафиксировать соглашение об извлечении полей из запроса/ответа через интерфейс `logged`.
8. Сопоставить конфигурацию (`logger.level`, `logger.time_format`) с её применением в коде.
9. Сформулировать правила с префиксом `LOG`; непоследовательные практики (например, несколько строковых уровней, схлопнутых в один) отметить явно.
10. Записать `docs/rules/logging.md` по формату из [template-rules.md](./template-rules.md) и проверить по чек-листу.

## Что выявлять

- Библиотека логирования (go-kit `log`/`level`) и формат вывода (структурированный JSON в stdout)
- Уровни логирования и их маппинг из строковой конфигурации
- Фолбэк-логгер и его инициализация в `init()`
- Передача логгера через `context.Context` (`WithContext`/`FromContext`)
- Middleware-декоратор логирования вызовов сервиса (паттерн обёртки `Service`)
- Стандартные поля сообщения: `ts`, `domain`, `method`, `took`, `code`
- Соглашение `logged`/`Log()` для извлечения полей из DTO
- Выбор уровня сообщения по результату (`Info`/`Warn`/`Error`)
- Конфигурируемость уровня и формата времени через секцию `logger`
- Запрет на использование стандартного `fmt.Print`/`log` для прикладного логирования (если наблюдается)

## Ограничения

- Источник — **только код проекта**; внешние эталоны логирования не используются.
- Описывается фактически используемая библиотека и приёмы; альтернативы (zap, zerolog, slog) не предлагаются, если их нет в коде.
- Sentry, метрики и трассировка как отдельные срезы наблюдаемости в этот документ не входят, кроме мест их пересечения с логированием.
- Команда не меняет код логирования — только создаёт/обновляет документ правил.
