# Команда: Извлечение правил TypeScript-стиля и написания кода

Изучает фактический стиль TypeScript-кода проекта и формирует документ правил `docs/rules/ts-style.md`. Процедурная инструкция для исполнителя (LLM-агент или разработчик), без привязки к конкретному агенту и переиспользуемая между TypeScript-проектами.

## Назначение

Вывести правила оформления TypeScript-кода из реальных файлов: иммутабельность (`readonly`, конструкторы, фабрики `create`), строгость типов и отношение к `any`, именование, обработка ошибок и асинхронность (`async/await`, отсутствие «плавающих» промисов), импорт типов, работа с константами и enum, декораторы и DI (если используется фреймворк вроде NestJS/Angular). Документ описывает то, как код **уже написан**, и закрепляет это как норму.

---

## Входные параметры

- Без обязательных аргументов — анализируется весь TypeScript-код репозитория.
- Необязательный аргумент `scope` — путь к подкаталогу (модуль, микросервис) для ограничения анализа.

## Источники в коде

| Что смотреть | Зачем |
|--------------|-------|
| `*.ts` в `src/` (`apps/`, `libs/`, `packages/`) | Основной стиль кода |
| Объявления `class` и их поля (`public readonly`, `private`) | Экспортируемость, иммутабельность, инкапсуляция |
| Статические фабрики (`static create(...)`) и конструкторы | Способ создания объектов вместо прямой мутации |
| Сигнатуры методов и функций (`async`, возвращаемый тип, позиция `Promise<T>`) | Асинхронность, явные типы возврата |
| `type` / `interface` / `namespace` / `enum` объявления | Конвенции типизации и группировки контрактов |
| `import type { ... }` против `import { ... }` | Политика импорта типов |
| Блоки констант, `enum`, union-литералы (`'ru' \| 'en'`) | Константы против магических значений |
| Имена классов, интерфейсов, функций, переменных, файлов | Конвенции именования |
| Использование `any`, `unknown`, `as`, `!` | Строгость типов и приведение |
| Декораторы (`@Injectable`, `@Controller`, `@Column` и т.п.) | Паттерны DI и метаданных |
| `tsconfig.json` (`strict`, `strictNullChecks`, `noImplicitAny`) | Уровень строгости компилятора |
| `package.json` | Версия TypeScript, фреймворк, зависимости |

## Алгоритм

1. Определить корень анализа (весь репозиторий или `scope`).
2. Прочитать `tsconfig.json`: зафиксировать уровень строгости (`strict`, `strictNullChecks`, `noImplicitAny`, `target`, `module`) — это база для правил типизации.
3. Собрать представительную выборку файлов из разных слоёв и модулей.
4. По выборке зафиксировать повторяющиеся приёмы: как создаются объекты (конструктор/фабрика), помечены ли поля `readonly`, есть ли мутации после конструирования.
5. Извлечь конвенции именования отдельно для классов, интерфейсов/типов, функций, констант, переменных, файлов (kebab-case, суффиксы `.entity.ts`, `.use-case.ts` и т.п.).
6. Определить политику типизации: отношение к `any`/`unknown`, приведению `as`, non-null `!`, явным типам возврата, `import type`.
7. Определить политику асинхронности: `async/await` против «сырых» промисов, обработка «плавающих» промисов, позиция `Promise<T>`.
8. Определить политику обработки ошибок: кастомные классы ошибок, `throw` против возврата результата, ранние возвраты.
9. Определить политику констант: union-литералы, `enum`, вынесение магических значений.
10. Если используется фреймворк (NestJS/Angular и т.п.) — зафиксировать паттерны DI, декораторов, конструкторной инъекции.
11. Сформулировать правила с префиксом `TS`; противоречивые практики отметить как частично соблюдаемые.
12. Записать `docs/rules/ts-style.md` по формату из [template-rules.md](./template-rules.md) и проверить по чек-листу.

## Что выявлять

- Иммутабельность: `readonly`-поля, заполнение только при конструировании, статические фабрики `create(...)`
- Способ создания объектов: конструктор против фабрики против объектного литерала
- Инкапсуляция: `private`/`public`/`protected`, отсутствие сеттеров
- Именование: классы, интерфейсы, типы, функции, константы, переменные, имена файлов и суффиксы
- Строгость типов: отношение к `any`, `unknown`, `as`, non-null `!`, явные типы возврата
- Импорт типов: `import type` для типов, разделение значений и типов
- Асинхронность: `async/await`, запрет «плавающих» промисов, позиция `Promise<T>`
- Обработка ошибок: кастомные ошибки, `throw`, ранние возвраты, оборачивание причины
- Константы против магических строк/чисел: union-литералы, `enum`, место объявления
- Организация контрактов через `namespace`/`interface`, если применяется
- Паттерны фреймворка: DI через конструктор, декораторы, `@Injectable`/`@Controller`
- Запреты, наблюдаемые в коде: глобальное состояние, мутируемые синглтоны, лишние комментарии

## Ограничения

- Источник — **только код проекта**; внешние гайдлайны (Airbnb, Google TS Style и др.) и другие документы проекта не используются как источник правил.
- Стиль выводится из наблюдаемого кода; если приём встречается непоследовательно — это отмечается явно.
- Правила форматирования (отступы, кавычки, точки с запятой) в этот документ не входят — они относятся к команде извлечения правил Prettier ([extract-prettier-rules.md](./extract-prettier-rules.md)).
- Команда не меняет исходный код — только создаёт/обновляет документ правил.
