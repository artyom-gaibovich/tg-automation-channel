# Команда: Извлечение правил API-контрактов

Изучает контракты API проекта (OpenAPI/Swagger, protobuf/gRPC, HTTP-хендлеры) и формирует документ правил `docs/rules/api-contracts.md`. Процедурная инструкция для исполнителя (LLM-агент или разработчик), без привязки к конкретному агенту.

## Назначение

Зафиксировать фактические нормы описания и реализации контрактов: структура `.proto`-файлов и их версионирование, размещение сгенерированного кода и client wrapper, спецификации OpenAPI/Swagger, конвенции HTTP-эндпоинтов, форматы запросов/ответов и коды ошибок. Документ выводит правила из реальных контрактов и хендлеров.

---

## Входные параметры

- Без обязательных аргументов — анализируется весь репозиторий.
- Необязательный аргумент `scope` — путь к подкаталогу (например, конкретный модуль или сервис).

---

## Источники в коде

| Что смотреть | Зачем |
|--------------|-------|
| `*.proto` (`api/proto/...`) | Структура контрактов, пакеты, версионирование, `go_package` |
| Сгенерированный код (`*.pb.go`, `*_grpc.pb.go`) | Размещение и изоляция транспортного слоя |
| gRPC server handler и client wrapper (`pkg/{module}/`) | Граница proto/gRPC, доменные интерфейсы |
| OpenAPI/Swagger (`openapi.*`, `swagger.*`) | REST-контракты, если есть |
| HTTP-хендлеры | Конвенции путей, методов, форматов, кодов ответов |
| Скрипты генерации (`scripts/protoc-*`, цели Makefile `proto`) | Процесс генерации кода |
| Маппинг ошибок в ответы | Конвенции кодов и форматов ошибок |

## Алгоритм

1. Определить корень анализа (весь репозиторий или `scope`).
2. Найти контракты: `.proto`, OpenAPI/Swagger, описания HTTP-эндпоинтов в коде.
3. Для protobuf: разобрать организацию файлов, версионирование (`v1` и т.п.), пакеты и `go_package`, размещение сгенерированного кода, наличие и роль client wrapper.
4. Зафиксировать процесс генерации кода (скрипты, цели Makefile, инструменты).
5. Для OpenAPI/Swagger: разобрать структуру спецификации, версионирование, схемы запросов/ответов.
6. Для HTTP/REST: вывести конвенции путей, методов, форматов данных, кодов ошибок, авторизации.
7. Зафиксировать изоляцию транспорта: где разрешены proto/gRPC-типы, где только доменные.
8. Сформулировать правила с префиксом `API`; непоследовательные практики отметить явно.
9. Записать `docs/rules/api-contracts.md` по формату из [template-rules.md](./template-rules.md) и проверить по чек-листу.

---

## Что выявлять

- Организация `.proto`: каталоги, версионирование, пакеты, `go_package`
- Размещение сгенерированного кода и его изоляция от вышестоящих слоёв
- Наличие и правила client wrapper (доменный интерфейс вместо proto-типов)
- Процесс генерации кода (инструменты, скрипты, цели Makefile)
- Структура OpenAPI/Swagger и версионирование контракта, если есть
- Конвенции HTTP: пути, методы, форматы запросов/ответов
- Коды ошибок и формат тела ошибки
- Механизм авторизации в контрактах
- Граница транспортного слоя: где разрешены proto/gRPC, где только домен

## Выходной артефакт

- Файл: `docs/rules/api-contracts.md`
- Префикс правил: `API`
- Формат: см. [template-rules.md](./template-rules.md)
- Фрагменты контрактов и кода приводятся из реальных файлов с указанием пути

---

## Ограничения

- Источник — **только контракты и код проекта**; внешние стандарты API не используются как источник правил.
- Если protobuf или OpenAPI в проекте отсутствуют — это фиксируется как «в проекте не обнаружено»; описываются только реально присутствующие виды контрактов.
- Команда не меняет контракты и код — только создаёт/обновляет документ правил.

## Чек-лист

- [ ] Найдены все виды контрактов (proto, OpenAPI/Swagger, HTTP-хендлеры)
- [ ] Разобрана организация и версионирование protobuf, если присутствует
- [ ] Зафиксированы размещение сгенерированного кода и роль client wrapper
- [ ] Описаны конвенции HTTP/REST и коды ошибок
- [ ] Описана граница транспортного слоя
- [ ] Каждое правило подтверждено фрагментом контракта/кода с путём к файлу
- [ ] Отсутствующие виды контрактов отмечены как «в проекте не обнаружено»
- [ ] Документ соответствует формату и содержит таблицу `API-NNN`
- [ ] Добавлена таблица версионирования
