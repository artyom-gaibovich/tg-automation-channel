# Команда: Извлечение правил работы с конфигурацией

## Назначение

Зафиксировать фактический способ конфигурирования сервиса: какой библиотекой читается конфигурация, в каком приоритете объединяются источники (флаги, переменные окружения, файл), как описывается структура конфига, какие параметры существуют и какие у них значения по умолчанию. Документ выводит нормы из реального кода конфигурации, а не из ожиданий.

---

## Входные параметры

- Без обязательных аргументов — анализируется весь репозиторий.
- Необязательный аргумент `scope` — путь к подкаталогу (например, конкретный микросервис) для ограничения анализа.

---

## Источники в коде

| Что смотреть | Зачем |
|--------------|-------|
| `configs/config.go` | Библиотека чтения конфига (viper/pflag), структура `Config`, метод `Read`, метод `Print` |
| Срез `options` (или аналог) | Перечень параметров, их типы, значения по умолчанию, описания |
| `viper.SetEnvPrefix`, `SetEnvKeyReplacer`, `AutomaticEnv` | Префикс и правила маппинга переменных окружения |
| Теги `mapstructure` в структурах конфига | Соответствие имён полей и ключей конфига |
| Вызовы `NewConfig`/`Read` в `cmd/`, `internal/server/` | Точка инициализации конфигурации |
| `.env`, `.env.example`, `*.toml` | Внешние источники значений и формат файла конфига |
| Использование полей конфига в коде | Как параметры доходят до слоёв (сервер, БД, логгер, sentry, tracer, limiter, metrics) |

## Алгоритм

1. Определить корень анализа (весь репозиторий или `scope`).
2. Найти пакет конфигурации (`configs/`) и определить используемую библиотеку и способ парсинга.
3. Разобрать структуру `Config`: вложенные секции, типы полей, теги `mapstructure`.
4. Извлечь полный перечень параметров из декларативного списка опций: имя ключа, тип, значение по умолчанию, описание.
5. Определить приоритет источников: флаги CLI → переменные окружения → файл; зафиксировать префикс окружения и правило замены разделителя (`.` → `_`).
6. Зафиксировать формат файла конфигурации (TOML) и способ его подключения.
7. Определить, где и как создаётся и читается конфиг (точка входа), как ошибки чтения оборачиваются и возвращаются.
8. Сопоставить секции конфига с потребителями (сервер, БД, логгер, sentry, tracer, limiter, metrics).
9. Сформулировать правила с префиксом `CFG`; непоследовательные практики (например, опечатки в дефолтах) отметить явно.
10. Записать `docs/rules/config.md` по формату из [template-rules.md](./template-rules.md) и проверить по чек-листу.

---

## Что выявлять

- Библиотека конфигурирования и способ парсинга (viper + pflag)
- Декларативный список параметров с типами, дефолтами и описаниями
- Приоритет источников: флаги > переменные окружения > файл
- Префикс переменных окружения и правило маппинга имён ключей
- Формат и подключение файла конфигурации (TOML, по флагу `config`)
- Структура `Config`: секции и теги `mapstructure`
- Точка инициализации конфига и обработка ошибок чтения/unmarshal
- Состав секций: server, logger, sentry, tracer, metrics, limiter, db
- Чувствительные значения по умолчанию (DSN, пароли) и отношение к ним

## Выходной артефакт

- Файл: `docs/rules/config.md`
- Префикс правил: `CFG`
- Формат: см. [template-rules.md](./template-rules.md)
- Каждое правило сопровождается фрагментом реального кода с путём к файлу

---

## Ограничения

- Источник — **только код и файлы конфигурации проекта**; внешние эталоны не используются.
- Отсутствующие источники (например, нет `.env.example`) не превращаются в правила; отмечаются как «в проекте не обнаружено».
- Команда не меняет код конфигурации — только создаёт/обновляет документ правил.
- Go-стиль самого пакета конфигурации в этот документ не входит — для него команда [extract-go-style-rules.md](./extract-go-style-rules.md).
