# Команда: Извлечение правил API-контрактов (TypeScript)

Изучает контракты API TypeScript-проекта (HTTP-контроллеры, DTO с валидацией, типы запросов/ответов, OpenAPI/Swagger, gRPC/protobuf, если есть) и формирует документ правил `docs/rules/ts-api-contracts.md`. Процедурная инструкция для исполнителя (LLM-агент или разработчик), переиспользуемая между TypeScript-проектами.

## Назначение

Зафиксировать фактические нормы описания и реализации контрактов: где живут типы запросов/ответов, как организованы DTO и валидация (`class-validator`, `zod`, `joi`), конвенции HTTP-эндпоинтов (пути, методы, коды ответов), форматы тела запроса/ответа и ошибок, версионирование, а также структуру `.proto`/OpenAPI при их наличии. Документ выводит правила из реальных контроллеров и контрактов.

---

## Входные параметры

- Без обязательных аргументов — анализируется весь репозиторий.
- Необязательный аргумент `scope` — путь к подкаталогу (например, конкретный модуль или сервис).

## Источники в коде

| Что смотреть | Зачем |
|--------------|-------|
| Контроллеры (`*.controller.ts`, декораторы `@Controller`, `@Get/@Post/@Patch/@Delete`) | Конвенции путей, методов, кодов ответов |
| Файлы контрактов (`*.types.ts`, `api-contracts/`, `dto/`) | Где и как описаны Request/Response, группировка через `namespace` |
| DTO-классы и декораторы валидации (`class-validator`: `@IsString`, `@IsOptional`, `@IsIn` и т.п.) | Правила валидации входных данных |
| `class-transformer` (`@Type`, `@Transform`) | Приведение и трансформация входа |
| `ValidationPipe`, глобальные пайпы/фильтры | Как включается валидация и обработка ошибок |
| Типы ответов (`Response.Data`, обёртки, пагинация) | Форматы тела ответа и конвенции пагинации |
| Маппинг доменных сущностей в ответ (форматтеры, presenters) | Граница домен → транспорт |
| Фильтры исключений / error-контракты | Конвенции кодов и формата тела ошибки |
| OpenAPI/Swagger (`@nestjs/swagger`, `openapi.*`), `.proto` (`api/proto/...`) | REST/gRPC-контракты, версионирование, генерация — если присутствуют |

## Алгоритм

1. Определить корень анализа (весь репозиторий или `scope`).
2. Найти контракты: контроллеры, файлы типов Request/Response, DTO, OpenAPI/Swagger, `.proto`.
3. Разобрать организацию контрактов: где лежат типы (в модуле рядом с контроллером или в общем каталоге), как группируются (`namespace Api { namespace <Endpoint> { Request/Response } }`, отдельные DTO-классы).
4. Вывести конвенции HTTP: базовые пути контроллеров, методы, параметры (`@Param`/`@Query`/`@Body`), коды ответов, формат тела.
5. Разобрать валидацию: библиотека, набор используемых декораторов, политика `@IsOptional`/значений по умолчанию, включение `ValidationPipe` и опции (`transform`, `whitelist`).
6. Зафиксировать формат ответа и ошибок: обёртки, пагинация, поля ошибки, статус-коды.
7. Зафиксировать границу транспорта: где разрешены транспортные типы (DTO), где только доменные сущности; как домен маппится в ответ.
8. Для gRPC/OpenAPI при наличии — разобрать организацию файлов, версионирование, процесс генерации кода (скрипты, npm-скрипты).
9. Сформулировать правила с префиксом `API`; непоследовательные практики отметить явно.
10. Записать `docs/rules/ts-api-contracts.md` по формату из [template-rules.md](./template-rules.md) и проверить по чек-листу.

## Что выявлять

- Размещение и организация контрактов (в модуле против общего каталога; `namespace` против плоских DTO)
- Конвенции HTTP: базовые пути, методы, параметры, статус-коды
- Библиотека и стиль валидации (`class-validator`/`zod`/`joi`), набор декораторов, значения по умолчанию
- Включение и опции `ValidationPipe`/пайпов
- Форматы тела запроса и ответа, конвенции пагинации и обёрток
- Формат и коды ошибок, error-контракты, фильтры исключений
- Граница транспортного слоя: где разрешены DTO, где только домен; способ маппинга в ответ
- Версионирование контрактов (URL-версии, заголовки, версии `.proto`)
- OpenAPI/Swagger и gRPC/protobuf: организация, генерация — если присутствуют

## Ограничения

- Источник — **только контракты и код проекта**; внешние стандарты API (REST best practices и др.) не используются как источник правил.
- Если OpenAPI/Swagger или protobuf отсутствуют — это фиксируется как «в проекте не обнаружено»; описываются только реально присутствующие виды контрактов.
- Команда не меняет контракты и код — только создаёт/обновляет документ правил.
