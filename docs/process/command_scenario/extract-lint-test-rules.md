# Команда: Извлечение правил линтинга и тестирования

Изучает конфигурацию линтеров и фактический стиль тестов проекта и формирует документ правил `docs/rules/linting-tests.md`. Процедурная инструкция для исполнителя (LLM-агент или разработчик), без привязки к конкретному агенту.

## Назначение

Зафиксировать фактические нормы контроля качества: какие линтеры включены и с какими настройками, какие проверки отключены и почему, как организованы тесты (структура, именование, моки, табличные тесты, e2e). Документ выводит правила из конфигурационных файлов и из самих тестов.

---

## Входные параметры

- Без обязательных аргументов — анализируется весь репозиторий.
- Необязательный аргумент `scope` — путь к подкаталогу для ограничения анализа.

---

## Источники в коде

| Что смотреть | Зачем |
|--------------|-------|
| `.golangci.yml` (или `.golangci.yaml`) | Включённые/отключённые линтеры, лимиты, исключения |
| `.go-arch-lint.yml` | Правила архитектурного линтинга, если есть |
| `Makefile` цели `lint`, `test`, `ci`, `fmt-check` | Как запускаются проверки в пайплайне |
| `*_test.go` по всему дереву | Структура и стиль тестов |
| Тестовые пакеты (`_test` suffix, `test/` каталоги) | Изоляция тестов, e2e |
| Использование `testify`, `mock`, `gomock` и т.п. | Подход к ассертам и мокам |
| Тестовые константы и хелперы | Конвенции тестовых данных |

## Алгоритм

1. Определить корень анализа (весь репозиторий или `scope`).
2. Разобрать конфигурацию линтеров: версия, таймаут, список включённых линтеров, список отключённых правил с обоснованиями (если указаны), лимиты (длина строки, сложность, длина функции), исключения по путям.
3. Если есть архитектурный линтер — извлечь его правила компонентов и зависимостей.
4. Зафиксировать команды запуска проверок из `Makefile`/скриптов.
5. Собрать выборку тестов и вывести конвенции: расположение тестов, имена функций, табличные тесты, библиотека ассертов, способ создания моков, организация e2e.
6. Определить политику тестовых констант и хелперов.
7. Сформулировать правила с префиксом `QA`; отключённые проверки описать с причиной, если она зафиксирована в конфиге.
8. Записать `docs/rules/linting-tests.md` по формату из [template-rules.md](./template-rules.md) и проверить по чек-листу.

---

## Что выявлять

- Линтер и его версия, таймаут запуска
- Включённые линтеры и их назначение
- Отключённые правила и зафиксированные обоснования
- Числовые лимиты: длина строки, цикломатическая сложность, длина функции
- Исключения по путям (`_test.go`, сгенерированный код, конфиги)
- Политика директив подавления (`//nolint:`)
- Архитектурный линтинг (компоненты, разрешённые зависимости), если присутствует
- Структура и именование тестов
- Подход к ассертам и мокам
- Организация e2e/интеграционных тестов
- Конвенции тестовых констант и хелперов

- Формат: см. [template-rules.md](./template-rules.md)

---

## Ограничения

- Источник — **только код и конфигурация проекта**; внешние стайл-гайды не используются.
- Если линтер не настроен или тесты отсутствуют — это фиксируется как «в проекте не обнаружено», без выдумывания правил.
- Команда не меняет исходный код и конфигурацию — только создаёт/обновляет документ правил.

## Чек-лист

- [ ] Разобрана конфигурация линтеров (включённые, отключённые, лимиты, исключения)

- [ ] Выведены конвенции структуры и стиля тестов
- [ ] Описаны подходы к ассертам, мокам и e2e
- [ ] Каждое правило подтверждено фрагментом конфига или теста с путём к файлу
- [ ] Документ соответствует формату и содержит таблицу `QA-NNN`
- [ ] Добавлена таблица версионирования
