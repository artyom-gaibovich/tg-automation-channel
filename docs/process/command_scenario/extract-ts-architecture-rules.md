# Команда: Извлечение правил архитектуры (TypeScript)

Изучает фактическую архитектуру TypeScript-проекта по исходному коду и формирует документ правил `docs/rules/ts-architecture.md`. Не зависит от конкретного LLM-агента — это процедурная инструкция для исполнителя (агент или разработчик), переиспользуемая между TypeScript-проектами (в т.ч. на NestJS/Angular/Express/Nest-подобных фреймворках).

## Назначение

Определить **фактический** архитектурный стиль проекта (слоистая, чистая, гексагональная, feature/module-first, transaction script и т.п.), направление зависимостей, состав слоёв, способ управления транзакциями и межмодульное взаимодействие. Результат — нормативный документ, выведенный из кода, а не из ожиданий.

Стиль не предполагается заранее: он распознаётся по структуре каталогов модулей, импортам и сигнатурам. Если код не соответствует ни одному «чистому» шаблону — это фиксируется как гибрид с описанием фактических свойств.

---

## Входные параметры

- Без обязательных аргументов — анализируется весь репозиторий.
- Необязательный аргумент `scope` — путь к подкаталогу (например, конкретный модуль или feature), чтобы ограничить анализ.

## Источники в коде

| Что смотреть | Зачем |
|--------------|-------|
| Дерево `src/modules/*` (или `src/features/*`, `apps/`, `libs/`) | Группировка по слоям или по доменным модулям |
| Подкаталоги внутри модуля (`domain`, `application`, `infrastructure`, `presentation`, `use-cases`, `ports`, `repositories`) | Наличие и назначение слоёв |
| Импорты между каталогами (относительные пути и алиасы `@/...`) | Фактическое направление зависимостей |
| Интерфейсы/абстрактные классы репозиториев и их реализации (`*.repository.ts` против `*.prisma-repository.ts`) | Инверсия зависимостей, изоляция ORM |
| Классы UseCase (`*.use-case.ts`, метод `execute`, `Input`/`Output`) | Способ оркестрации бизнес-операций |
| Доменные сущности (`*.entity.ts`), их конструкторы и фабрики | Что относится к домену |
| `*.module.ts` (NestJS) — `imports`, `providers`, `exports`, DI-токены | Границы модулей и способ связывания слоёв |
| Управление транзакциями (Unit of Work, `$transaction`, `prisma.$transaction`, `QueryRunner`) | Где и как живут транзакции |
| Точки межмодульного взаимодействия (инъекция сервисов, события, HTTP/gRPC-клиенты) | Допустимые способы связи модулей |

## Алгоритм

1. Определить корень анализа (весь репозиторий или `scope`).
2. Построить карту модулей и каталогов: для каждого — роль слоя и во что он импортирует (учесть алиасы путей из `tsconfig.json`/`nest-cli.json`).
3. По карте импортов установить **направление зависимостей** между слоями и проверить нарушения (например, `domain`, импортирующий `infrastructure` или сторонний ORM).
4. Классифицировать стиль: сопоставить наблюдаемую структуру с известными шаблонами (layered / clean / hexagonal / module-first по доменам / transaction script). Зафиксировать признаки вывода.
5. Выделить повторяющиеся инварианты: что всегда в `domain`, что в `application`, что в `infrastructure`, что в `presentation`; как именуются UseCase; где объявлены порты/интерфейсы.
6. Зафиксировать способ связывания слоёв через DI-контейнер фреймворка (`providers`/`exports` в `*.module.ts`, токены, абстрактные классы как токены).
7. Описать управление транзакциями как наблюдаемый паттерн.
8. Описать межмодульное взаимодействие: только через публичные `exports`/интерфейсы/события или есть прямые глубокие импорты внутренностей чужого модуля.
9. Сформулировать каждое наблюдение как правило с ID-префиксом `ARCH`.
10. Записать документ `docs/rules/ts-architecture.md` по формату из [template-rules.md](./template-rules.md).
11. Проверить документ по чек-листу.

---

## Что выявлять

- Архитектурный стиль и признаки, по которым он определён
- Состав слоёв и зона ответственности каждого (`domain`/`application`/`infrastructure`/`presentation`)
- Направление зависимостей и явные запреты (что какому слою импортировать нельзя, изоляция ORM в инфраструктуре)
- Где объявляются порты/интерфейсы и где реализуются (инверсия зависимостей)
- Разделение чтения и записи, если присутствует
- Структура UseCase: метод `execute`, типы `Input`/`Output`, единичность операции
- Способ связывания слоёв через DI (`*.module.ts`, provider-токены, абстрактные классы)
- Паттерн управления транзакциями
- Правила межмодульного взаимодействия и границы публичного API модуля (barrel-файлы `index.ts`, `exports`)
- Группировка кода: по слоям или по доменным модулям

## Выходной артефакт

- Файл: `docs/rules/ts-architecture.md`
- Префикс правил: `ARCH`
- Формат: см. [template-rules.md](./template-rules.md)
- Каждое правило сопровождается фрагментом реального кода проекта (путь к файлу указывается рядом с примером)

---

## Ограничения

- Источник — **только код проекта**; запрещено переносить правила из внешних эталонов или из других документов проекта.
- Запрещено выдавать желаемую архитектуру за фактическую: если код противоречив, документ описывает противоречие.
- Если слой или паттерн в коде отсутствует — он не упоминается как правило (либо отмечается «в проекте не обнаружено»).
- Команда не меняет исходный код — только создаёт/обновляет документ правил.

## Чек-лист

- [ ] Построена карта модулей и импортов (с учётом алиасов путей)

- [ ] Архитектурный стиль классифицирован с указанием признаков
- [ ] Описаны инверсия зависимостей и способ связывания через DI
- [ ] Описаны транзакции и межмодульное взаимодействие
- [ ] Каждое правило подтверждено фрагментом кода с путём к файлу
- [ ] Документ соответствует формату и содержит таблицу правил `ARCH-NNN`
- [ ] Добавлена таблица версионирования
